## Context
Brief 007's weight sweep was planned as 672 jobs of 1,000 games, about 3 hours inside a Claude session. That has three costs:
- The session is tied up, and can be stopped partway.
- Every check-in on a batch uses the Editor's Claude allowance.
- The results end up in `data/sim_studyN` folders whose names don't say which version they tested, why they were run, or when.

GitHub runs jobs free for a public repo, up to 20 at once, and already runs the nightly checks.

**The Editor's direction (18 Nov):**
- Run the checks on GitHub: small runs during the day, big runs overnight.
- Keep the results organised so any later chat can find them.
- Save each game's seed, so a strange result can be replayed.
- Measure everything from the same games, since they're being played anyway.
- Build a clear structure that doesn't trap us: new kinds of run, new measures and new formats (Cavalry, 9v9, specials, other brains) must fit without reorganising.

The design chat is the main reader of these results. The Editor reads the summaries when he wants to.

## What to build

### 1. One results folder, one shape per run
```
results/
  README.md          how this folder works: the kinds, the naming rules, the file formats, how to add a new kind
  INDEX.md           one line per run, newest first, written automatically
  index.csv          the same list for scripts: id, date, version, kind, brief, tags, question, answer, path
  v3.06.00/          runs grouped under the game version they tested
    2026-11-19_study_brain6-vs-brain5/
  pre-v3.05.00/      the old data/sim_study6–10, moved as they are, with a README saying what each was
```

**Folder names:** `YYYY-MM-DD_kind_short-topic`. The date is the date it ran, in New York time. The topic is lowercase with hyphens. A second run of the same thing on the same day gets `-2`.

**Kinds** are an open list, kept in `results/README.md`. Adding one means adding a line there; no code should refuse an unknown kind. Start with:
- `screen`: a quick daytime look, up to about 200 games per side.
- `study`: a big run answering one question from a brief, usually overnight, 1,000+ games per side.
- `release`: a version's final exam (item 4).
- `nightly`: the health check on `main` (item 5).

**Every run folder has the same core files:**
- `SUMMARY.md`, read first. Always in this order:
  - the question
  - the answer in one line
  - the key table
  - likely or proven
  - flags raised
  - how to replay the odd games.

  One screen at most. Tiebreak wins always counted apart from KOs and draws.
- `run.json`, the facts. Core fields:
  - `id`, `kind`, `version`, `build`, `commit`, `brief`
  - `question`, `tags` (a free list, e.g. `["brain6","stalls","evade"]`)
  - `trigger` (night, day or pull request), `started`, `finished`
  - `games`, `seed_from`, the scripts and their arguments, the settings used.

  Anything else goes under `extra`. New fields are allowed; nothing should break on a field it doesn't know.
- `games.csv`, one row per game, plus a `replay` link (item 3). Core columns:
  - `seed`, `version`, `rules`, `format`, `lineup_n`, `lineup_s`, `brain_n`, `brain_s`, `first`
  - `winner`, `how`, `turns`, `flag_damage_n`, `flag_damage_s`, `units_lost_n`, `units_lost_s`.

  Any other measure is an extra column. New measures add columns; they never rename or remove core ones. Gzip it if it's over about 5 MB.
- `tables/`, the totals behind the summary, as CSV.

**What's kept:**
- Everything above, in the repo, forever.
- Turn-by-turn logs as GitHub downloads (artifacts) for 90 days, since the seed rebuilds any game.

### 2. The lab workflow
A new workflow, `lab.yml`, plays **job orders**:
- A job order is a small JSON file in `studies/queue/`, written by the design chat (in a brief) or by Code during a build.
- It says: id, kind, brief, question, tags, and a list of matchups. Each matchup gives the brains, rule set, format, lineups, games and seed range, plus which measures to collect.
- Measures are named in a list, so a new measure is a new name and a new function, not a new workflow.
- The workflow splits the games across up to 20 GitHub machines, merges them, writes the run folder, adds the INDEX line, and moves the job order to `studies/done/`.

When it runs:
- **Every night**, after `main`'s nightly check, it plays whatever is queued.
- **On demand** at any time ("Run workflow"), so Code can start a daytime `screen` and keep working while it runs.
- If Code's session can't start a workflow, say so in the Report as an `ASK`, and daytime screens stay in the session for now.

How results get back:
- Results reach `main` without the Editor clicking anything. They may only change `results/` and `studies/`.
- Recommended: an automatic pull request that merges itself once checks pass.
- If `main`'s protection blocks that, raise an `ASK` with the simplest option.

A job that fails writes a run folder anyway, with `SUMMARY.md` saying what failed, and opens or adds to a GitHub issue, as the night checks do now.

### 3. Every simulated game can be watched on the board
Today the sims seed games from `tests/rng.js`, and the board seeds matches from its own "Game seed" (for example TJBH-QBDJ-395W). So a sim game can't be found on the board. Change the sims so that:
- `tests/rng.js` deals each game a board seed. It stays the only random source the sims draw from.
- Each game is then played exactly as the board would play a Computer vs Computer match with that seed, those brains, that rule set, format and lineups.
- `games.csv` gets a `replay` column: a link to the live board that opens that match set up and ready to watch, for example `https://productofdefiance.github.io/Flagfall/?watch=…`. The board needs a small addition to read the link and fill in the setup.
- If that version's brain or rule set is no longer on the board, the board says so plainly instead of playing a different game.

Add a check that 10 sim games and the same 10 games set up on the board give identical moves (same hash).

### 4. Release runs: a version's final exam
On any pull request that raises the game version, the lab runs a `release`:
- every check in `README.md`
- the replay and regression hashes
- the baseline table (holder KO, pull KO, TKO, tiebreak win, draw, ended on the turn limit, games with a pull, average turn, first mover's share), at 1,000 games per format, newest rule set, default brain mirror.

Its `SUMMARY.md` is posted as a comment on the pull request. After the merge, the folder is stored under that version. One release per version: the Editor's answer to "what did this version's checks say".

### 5. Nightly
Fold the existing night checks into the same results system:
- If `main` hasn't changed since the last passing night, it adds one INDEX line ("no change, passed") and no folder.
- Otherwise it writes a `nightly` folder.
- Keep the failure issue.

### 6. Tidy the repo
- `board/tests/` keeps only pass/fail checks (`test_*.js`, `regress_engine.js`, `rng.js`).
- Scripts that play games and make results move to `sims/`. That includes `baseline.js`, `h2h*.js`, `sim_games.js`, `flagdiag.js`, the Python summarisers, and the scripts in `data/sim_study10/`.
- Move `data/sim_study6–10` to `results/pre-v3.05.00/` with `git mv`, so history is kept. Add a README listing each old study: what it asked, which brief, which rule set and brains. Don't rewrite old briefs; the README maps old paths to new ones.
- `data/human_matches.csv` and `data/match3_log.txt` stay in `data/`. That folder is for records that aren't simulation results.
- Update `README.md` and every workflow for the new paths.

### 7. Add to `CLAUDE.md`
- **Where runs happen.** Simulations run on GitHub through the lab, not in a Claude session. Daytime `screen` runs are for quick looks; anything at 1,000+ games per side goes overnight. A short check during a build is fine in the session.
- **Sweeps in two stages.** Screen every value at about 200 games per side. Confirm only the promising ones at 1,000+ overnight (F23).
- **Results.** Every run writes a folder in `results/` as `results/README.md` describes. Never put results anywhere else. Extend the structure by adding (a kind, a column, a field), never by renaming.
- **Version at merge.** A brief states the version it expects. If another pull request merged first, take the next free number and fix `version.js` and the changelog heading.
- **Side by side.** Two builds may run in parallel unless one changes what the other measures or shows. Rule changes go one at a time. Branch from `main` (or the brief branch), never from another open pull request.
- **Branch names.** Use whatever branch the session may push to. Start it from the brief branch, and name it in the Report.

- **What will strain first as Cavalry, 9v9 and more brains arrive:**

  3. **Board seeds and old versions.** A replay link only replays exactly on a board that still has that brain and rule set unchanged. The board refuses missing ones and warns on a different version, but a brain tuned under the same id (Brain 6 after brief 007) would replay differently on a newer board. Keeping each version's board online (a tag per version) would fix that; not built.
