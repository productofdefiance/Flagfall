# Brief 002 — v3.2: order of operations

| | |
|---|---|
| Rule set | v3.2 (new preset, copied from v3.1) |
| Date | 17 Nov 2026 |
| Goal | Every exchange has an order of operations, so exactly one unit survives it, and no single action can end the match for both sides. |
| Branch | `build/002-v3.2-order-of-operations` |
| Flags | F3, F4, F5, F17, F18 |

## Context
The Editor's principle (ruled 17 Nov): a unit that dies can't strike back, so two units never trade fatal blows in one action. Today a Heavy Melee killed by an attack still parries, which can remove its attacker too. v3.1's fallback gives a double knockout to the side that acted. The Editor ruled that a double knockout should go to the turn-limit tiebreaks instead. In practice, once dead units can't parry, a double knockout should never happen. This build proves that. It also brings in a second decided parry rule (Game Laws 6.3: parry fires on the first attack only each enemy turn), so both parry changes share one new preset and one baseline run. And it closes two gaps Code found in Brief 001: the impossible-state check only plays v3 (F17), and the regression hashes leave v3.1 out (F18).

## Scope
In: a new preset v3.2 with three switches, tests, an impossible-state test for the newest preset added to `checks`, and v3.1 added to the regression hashes. Out: everything else, including any bot change.

## What to build
1. **New preset `v3.2`**, a copy of `v3.1`, added as the last entry in `PRESETS` so it becomes the new-game default. Note: "v3.1 plus: dead units don't parry; parry once per enemy turn; a double knockout goes to the tiebreaks."
2. **Switch `parryNeedsSurvivor`** (on in v3.2): parry fires only if the braced unit still has more than 0 HP after the hit. A unit removed by the hit deals no parry.
3. **Switch `doubleKoToTiebreak`** (on in v3.2; `simultaneousToActor` off in v3.2): if one action leaves both sides with a KO or TKO, the match is settled by the same order the turn limit uses: more pull damage, then fewer beings lost, then a draw. The result's `how` must make clear it came from a double knockout (for example `"double knockout, more pull damage"`).
4. **Switch `parryFirstOnly`** (on in v3.2): a braced unit's parry fires only on the first attack against it in each enemy turn, at 20% as now. Later attacks that turn get no parry. It resets when that side's next turn begins. If the first attack kills the braced unit, no parry fires (item 2).
5. **Tests** in a new `board/tests/test_v32.js`:
   - a braced Heavy Melee killed by an adjacent attack deals no parry on v3.2, and does deal it on v3.1 (fails before, passes after);
   - a braced Heavy Melee that survives still parries on v3.2;
   - a braced Heavy Melee hit twice in one enemy turn parries the first attack only on v3.2, and both on v3.1 (fails before, passes after); in the next enemy turn it parries the first attack again;
   - a hand-built position where one action finishes both sides resolves by the tiebreaks on v3.2 (force it with set spear or a test-only state if parry can no longer cause it);
   - **double-knockout count:** 400 seeded bot games at 7v7 and 400 at 5v5 on v3.2 (Kit B vs Kit B, balanced lineups, `tests/rng.js`). Count actions after which both sides had a win condition. Expected: 0. Print the count; fail the test if it is above 0.
6. **Impossible-state test for the newest preset (F17)** in a new `board/tests/test_invariants.js`: plays 30 seeded bot games on the last entry in `PRESETS` (so it follows each new preset automatically), taking randomness from `tests/rng.js`, and fails on any impossible state that `redteam/invariants.js` checks for (two units on a hex, HP outside its range, negative Stamina, a refused bot action, a bot error). Add it to the `checks` workflow. Keep the existing `redteam/invariants.js` run: it still guards v3.
7. **Regression hashes include v3.1 (F18):** change `regress_engine.js` so it leaves out only the newest preset, not v3.1 by name. Record v3.1's hash from the board as it is before any engine change in this build.
